# 設計書: SODA記事品質強化（取材・視点・文体）

日付: 2026-08-11
状態: 承認済み（CEO=ユーザー承認）

## 背景と目的

デイリーパイプラインは全自動で安定稼働しているが、記事に3つの課題がある。

1. **取材の浅さ** — 情報源が WebSearch 2クエリのみ。一次情報に当たらず孫引きで書いている
2. **視点の独自性不足** — 他のまとめ系と同じニュースを同じ角度で解説しており、SODAで読む理由が弱い
3. **AIっぽい文体** — voice_guide 照合が Writer/Editor の自己申告のため、AI臭が残る

完全自動運転は維持したまま、工程の追加・改修で3課題を構造的に解決する。

## 変更しないもの

- cron 設定（時刻・ジョブ構成）
- note / X への公開フロー（`note_post.py` / `x_post.py`）
- 朝会議・投稿分析・アイデア発掘などパイプライン外のジョブ
- 人の関与ゼロという運用形態

## 変更1: Step 1.5「Researcher」取材工程の新設

**位置**: Step 1（CEOテーマ決定）と Step 2（Planner企画）の間。採用テーマ1本のみを深掘りする（全候補の深掘りはしない）。

**Step 0 の拡張**: 検索クエリを2本から4本に増やす。

- 現行: `"AI news today {ds}"` / `"生成AI ニュース {ds}"`
- 追加: `"AI layoffs OR funding OR acquisition {ds}"` / `"AI industry news {前日}"` （英語圏の資金・雇用・構造転換ニュースの取りこぼし防止）

**Researcher の作業内容**（`agents/researcher.md` に定義）:

1. 採用ニュースの一次情報（公式発表・プレスリリース・元記事）を WebFetch で読む
2. 英語ソースを含む追加検索を3〜5本行う
3. 反対意見・懐疑的な見方を最低1つ探す
4. 比較に使える過去の数字（前年・前四半期・類似事例）を集める

**成果物**: 取材ノート `content/news/{ds}_research.md`。構成は4区分固定:

```
## 確認できた事実（各項目に出典名を付す）
## 数字一覧（数値・単位・出典・時点）
## 反対意見・留保
## 未確認事項（検索したが裏取りできなかったこと）
```

**Writer への新ルール**（`agents/writer.md` に追記）:

- 記事中の事実・数字は取材ノートに記載のあるものだけを使う。ノートにない数字は書かない
- 「未確認事項」に載っている内容は、本文でも未確認・報道ベースであると明示する

**フォールバック**: 取材ノートの生成に失敗した場合、Writer は現行同様 Step 0 の検索結果ベースで執筆してよい（パイプラインは止めない）。

## 変更2: SODA視点ライブラリ `docs/perspectives.md`

**目的**: 単発解説の寄せ集めから「継続性のある定点観測メディア」への転換。持論と伏線の蓄積・回収で、まとめ系との差別化を作る。

**ファイル構成**:

```
## 持論（SODAのスタンス。例: レイオフはAI代替でなく組織再設計の話）
## ウォッチ中の仮説（最大15件。各項目に「回収予定時期」を付す）
## 回収済みアーカイブ（回収した仮説と、当たり外れの記録）
```

**参照（書くとき）**:

- CEO（Step 1）: 回収期限が到来した仮説があれば、その日のテーマ候補として最優先で検討する
- Writer（Step 4）: perspectives.md を必ず読み、接続できる持論・伏線があれば「以前から〜と見ている」「◯月に書いた◯◯がここに繋がる」と本文で明示的に接続する

**更新（Step 7.5、Secretary の後に新設)**:

- その日の記事から新しい仮説・伏線を「ウォッチ中」に追記する
- 回収した仮説は結果（当たり/外れ/部分的）を添えてアーカイブへ移動する
- 「ウォッチ中」が15件を超える場合は、古い・弱いものからアーカイブへ落とす

**初期データ**: `content/note/` の過去記事から持論・未回収の伏線を抽出して初期版を生成する（実装タスクに含む）。

## 変更3: Step 5.5「Critic」敵対的批評ループ

**位置**: Step 5（Editor仕上げ）と Step 6（CEO最終判断）の間。対象は note 記事本文。

**Critic の作業内容**（`agents/critic.md` に定義）:

- voice_guide の「AI臭いパターン一覧」との照合
- 独自観点: 構造が整いすぎていないか / 締めが教訓化していないか / 声に出して読めるリズムか / 実感のない一般論で埋めていないか
- 10点満点で採点し、**必ず直せる欠点を3つ以上、修正指示として挙げる**（褒め禁止の敵対的スタンス）

**ループ**: 7点未満なら Editor が修正指示に従って書き直し、Critic が再採点する。最大2周で打ち切り、打ち切り時は最終稿のまま Step 6 に進む（CEO 側の減点判断に委ねる）。

**既存の Step 6 CEO 推敲ループ（最大3回）は現行のまま維持する。**

## エラー処理方針

既存方針を踏襲する。新工程の失敗はパイプライン全体を止めず、フォールバック（取材ノートなし執筆・Critic スキップ）で公開まで到達させる。失敗は既存の `notify_error.py` 経路で通知される。

## 検証方法

当日分のコンテンツは生成済みのため、`run_daily.sh` を再実行しても既存ファイル検知でスキップされる（仕様）。よって検証は次の2段で行う。

1. **実装直後**: `build_pipeline_prompt()` の出力を目視確認し、新Step（0拡張・1.5・5.5・7.5）が正しい位置・正しいファイルパスで含まれることを確認する。`perspectives.md` 初期版と新エージェント定義2本の内容を確認する
2. **翌朝の cron 実行後**: `content/news/{ds}_research.md` の生成、記事本文での視点接続、`perspectives.md` の更新、`logs/cron/{ds}_run.log` 内の Critic 採点を確認する
